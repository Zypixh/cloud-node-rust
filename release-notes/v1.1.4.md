# cloud-node-rust 1.1.4

## 概述

1.1.4 聚焦控制面协议、NodeStream 稳定性、缓存任务语义、缓存主域名兼容、双栈监听和 UDP 会话生命周期。节点侧 gRPC 控制流统一回到 tonic generated client，缓存刷新/预热不再把控制面 URL 当作简单 HTTP 请求，而是按本地站点路由、泛域名匹配、location 缓存配置和 `web.cache.key` 主域名规则生成真实缓存 key。

## gRPC / tonic 替换计划与控制流

- 替换计划：NodeStream 运行主路径统一使用 tonic generated client，移除手写 h2/gRPC framing 主路径；保留的协议处理只负责消息解释、任务分发和探测统计。
- tonic client 分层：NodeStream 使用 plain client；其他一元 RPC 继续沿用现有 client 工厂和 metadata 注入逻辑。
- NodeStream 不对 bidi stream 强制 gzip，避免控制面兼容风险。
- 等待 response headers 或下行消息期间继续发送 ping，避免服务端暂未下行时客户端自己按 30 秒超时断开。
- NodeStream 探测结果可以区分 transport 已打开、ping 已发送、控制面未下行消息三种状态，减少误判。
- gRPC metadata 插入去掉 panic 路径，异常 nodeId/token 不会直接终止缓存任务或控制流。

## 缓存 API 不兼容与修复

- 不兼容点：控制面 `writeCache`、`readCache`、`statCache`、`cleanCache` 是节点本地缓存操作，不是可路由 URL 请求；Rust 侧已改为直接调用 cache manager/storage。
- 不兼容点：Go `[]byte` 在 JSON 中会表现为 base64 字符串；Rust 侧已兼容 `cachePolicyJSON`、value 等 bytes 字段的解析。
- 不兼容点：`writeCache` payload 会携带 cache policy JSON；Rust 侧会先应用 policy，再写入对应 key，避免按默认策略写错缓存元数据。
- `readCache` 返回本地缓存 value size，`statCache` 返回本地缓存对象数量和大小，`cleanCache` 执行本地清理并返回结果。

## 缓存刷新 / 预热任务

- 节点侧缓存任务使用最新 `HTTPCacheTaskKeyService.findDoingHTTPCacheTaskKeys` 和 `updateHTTPCacheTaskKeysStatus`。
- 支持 `purge`、`preheat` 和兼容类型 `fetch`；支持 key、prefix/directory、site/all、tag/surrogate-key。
- purge 任务按当前 ConfigStore 定位 server，再按站点或 location 的 `web.cache.key` 生成实际缓存 key。
- 站点级/目录级刷新会转换为有 host/path 边界的 prefix，拒绝 `*`、裸 scheme、裸 host 等危险全局删除。
- purge 会同时扩展 http/https counterpart，兼容控制面任务 URL scheme 与本地缓存 key scheme 不一致的情况。
- key/prefix purge 会同步清理 partial cache、磁盘对象、元数据索引、surrogate index、FAST_L1 内存命中和 Pingora MemCache，避免清理后继续从内存返回旧对象。
- RKE2 模式下 key、prefix、tag purge 会通过内部 API fanout 到其他副本。
- preheat 改为节点主动回源：请求固定 resolve 到本机代理，通过本地 HTTP/HTTPS 路由、缓存规则和 cache key 生成逻辑写入缓存。
- preheat 任务 key 如果是缓存主域名但不是精确站点名，会改用可路由站点 host 请求本机代理；如果缓存主域名本身是精确站点名，则保持原 URL，避免改变回源 Host。
- HTTPS preheat 固定走本机 loopback，允许本机无效证书，避免 dev/default cert 或证书同步窗口导致预热失败。
- 本地 HTTP `PURGE` 请求在通过站点 purge key 授权后，会调用 `ServerService.purgeServerCache` 通知控制面。

## 缓存主域名

- 接收并使用控制面 `web.cache.key.isOn`、`web.cache.key.scheme`、`web.cache.key.host`。
- HTTP 缓存 key 生成时，`${scheme}` 和 `${host}` 会被覆盖为配置的缓存主域名。
- purge/preheat 也使用同一套缓存主域名规则，避免请求域名和缓存 key 域名不一致导致刷新失效。
- location 级 cache key 优先于站点级 cache key，匹配路径下的刷新会落到 location 配置的主域名。
- 真实配置验证中，wildcard 站点和对应精确站点同时下发，缓存主域名配置为同一精确域名，scheme 为 `https`。
- 本地 dev 验证中，一级子域首次写入后，根域和多级子域命中同一缓存对象；缓存文件 hash 等于缓存主域名 URL 的 MD5，确认 key 聚合到主域名而非请求域名。

## 泛域名路由

- L7 HTTP 路由支持 `*.example.com` 同时匹配根域、一级子域和多级子域。
- TLS/SNI L7 路由使用同样的 wildcard 语义，避免 HTTPS 与 HTTP 命中行为不一致。
- purge/preheat 的 host 校验也接受 wildcard 站点名和配置的缓存主域名。
- 精确域名优先于 wildcard；SNI passthrough 与 L7 wildcard 的优先级保持原有隔离。

## 监听双栈与 UDP 会话

- HTTP/HTTPS、TCP/TLS、UDP 和 QUIC/HTTP3 demux 入口监听改为显式双栈 socket：同一业务端口同时绑定 `0.0.0.0:port` 和 `[::]:port`。
- IPv6 监听显式设置为 v6-only，避免依赖系统默认 dual-stack 行为，也避免 `[::]:port` 与 `0.0.0.0:port` 互相抢占。
- listener 生命周期从仅按端口跟踪改为按 `SocketAddr` 跟踪，避免同端口的 IPv4 和 IPv6 listener 在热加载时互相覆盖。
- UDP passthrough 后端会话改为 connected UDP，使用 `connect + send/recv` 与选定源站通信；临时本地端口仍由系统分配，但不再以无连接 `0.0.0.0:*` wildcard UDP socket 形式出现在 `netstat -l` 中。
- UDP 空闲会话、监听端口移除和热加载清理会主动通知会话任务退出，及时释放后端临时 UDP socket。

## 缓存 API 调用审计结论

节点运行时应调用并已覆盖：

- `HTTPCacheTaskKeyService.findDoingHTTPCacheTaskKeys`
- `HTTPCacheTaskKeyService.updateHTTPCacheTaskKeysStatus`
- `ServerService.purgeServerCache`

节点运行时不应主动调用：

- `NodeService.updateNodeCache`：管理侧更新节点缓存配置接口。
- `HTTPCacheTaskKeyService.validateHTTPCacheTaskKeys`、`countHTTPCacheTaskKeysWithDay`：管理/统计链路。
- 旧 Go 侧或管理侧资料中出现的 `HTTPWebService.updateHTTPWebCache`、`HTTPCacheTaskService` 等接口未出现在当前 Rust `proto_defs/output_protos` 中，不作为节点侧待补调用项。
