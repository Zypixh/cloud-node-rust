# 禁止未经审批的功能降级

本文件是项目的强制工程约束，适用于人类开发者和所有 AI agent 工具。

本项目不得为了让测试、请求或任务"继续成功"，未经用户明确审批就引入或扩大降级行为。

> 本文件是唯一事实来源。`.cursor/rules/no-unapproved-degradation.mdc` 是本地镜像，只保留摘要。
> 修改规则时改这里。

## 必须遵守

- 不得静默禁用功能、协议路径、缓存层、L1/L2、压缩、partial cache、PURGE、集群同步或一致性检查。
- 不得把错误改成旁路、cache miss、origin fallback、旧数据继续服务、空结果、丢弃事件或 best-effort success。
- 不得吞掉错误、忽略失败返回值、降低校验强度、缩短超时、减少重试，或通过 catch/默认值掩盖根因。
- 不得用 `#[allow(...)]`、`--cap-lints`、`-A warnings` 一类手段把编译期警告压下去——
  屏蔽警告是"掩盖根因"的同类操作。详见 [警告与 lint 策略](warning-and-lint-policy.md)。
- 不得以"安全""保守""兼容""性能优化"为理由改变语义，除非明确说明这是降级并获得审批。
- 发现现有代码已经降级时，先报告触发条件、影响和证据；不要在未审批的情况下继续扩展该模式。

## 审批要求

只有用户在当前任务中明确同意具体降级方案后，才可以实施。审批必须绑定：

1. 触发条件和受影响的功能范围；
2. 原行为与降级后行为；
3. 对正确性、一致性、可用性和可观测性的影响；
4. 恢复条件、迁移计划或移除条件；
5. 覆盖正常路径、错误路径和恢复路径的测试。

如果需求不明确，必须先询问用户，不得自行选择降级作为默认方案。审批只授权所描述的范围，不能推导出其他降级权限。

## 允许的安全处理

安全策略要求的 fail-closed 拒绝不是功能降级，但必须：

- 明确记录拒绝原因，不能伪装成普通 miss 或成功；
- 保留可观测的日志、指标或错误状态；
- 不改变无关功能的行为；
- 增加回归测试，证明恶意或不安全输入不会被错误接受。

## 报告要求

实现完成后，最终报告必须区分：已修复问题、仍存在的问题、设计限制，以及任何经审批的降级。
